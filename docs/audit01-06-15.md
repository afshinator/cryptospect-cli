## Code Verification & Fix Analysis (2026-06-15)

Each audit finding was investigated against the actual source code. Findings and
suggested fixes below.

### 1. Dominance delta_pp = 0.0000 — Not a bug, rapid-run artifact

**Code traced:** `internal/metrics/dominance/v1/compute.go:12-47`, `provider.go:50-88`

**What happens:**

The dominance provider maintains a state cache (`dom_btc_dominance_pct`,
`dom_eth_dominance_pct`, TTL=48h). On each invocation:

1. Opens cache → reads prior values
2. Computes delta = current − prior
3. Writes current values to cache

If no prior exists → cold start → `delta_pp` field omitted from JSON (nil pointer).
If prior exists and ≤24h old → delta computed normally. If prior >24h old → treated
as cold start (`MaxSnapshotAgeSec = 86400` at `types.go:43`).

In the audit run, all three `dom` calls happened within the same second (the
all-metrics loop runs basic→extended→full without pause per metric). The first
call populated the cache; the second and third calls read the freshly-written
entry with `ageSec ≈ 0`. Current and prior values were identical (same
CoinGecko response, same cache window), producing `delta = 0.0000`.

The first call's prior was also ≤24h old (prior session cache), so delta was
computed but happened to be near-zero within the dead band (±0.5pp BTC, ±0.3pp ETH).

**Verdict:** Code logic is correct. The delta value is mathematically accurate for the
lookback window available. The audit's concern is valid from a UX perspective: seeing
exactly `0.0000` for both assets suggests something is wrong when in fact the data
just hasn't moved significantly.

**Suggested fix (low):**
- Add a minimum lookback gate in `compute.go`: if `priorAge < MinLookbackSec`
  (e.g., 300s), use neutral trend with a note like `"trend_unavailable"` and
  omit `delta_pp`. This prevents the misleading `0.0000` when the prior snapshot
  is too recent to produce a meaningful trend signal.
- Alternatively, surface the lookback window in the summary text.

### 2. Flow Tension — CVD classification is correct, thresholds hidden

**Code traced:** `internal/metrics/flowtension/v1/compute.go:84-94`, `types.go:19-21`

**What happens:**

CVD ratio 0.4528 is classified via `ComputeFlowHook()`:

```
netFlow ≥ FlowAggressiveThreshold (0.10) → "aggressive_buy"
netFlow ≤ −0.10 → "aggressive_sell"
else → "neutral"
```

0.4528 ≥ 0.10 → `"aggressive_buy"`. Math is correct.

The problem: `FlowAggressiveThreshold = 0.10` is a Go constant (`types.go:20`).
It only appears in output at `--detail full` because `"thresholds"` is in
`fullDetailOnlyFields` (`cmd/cryptospect-cli/meta_processing.go:12`).

At `--detail basic` or `--detail extended`, the consumer sees `"hook": "aggressive_buy"`
with no way to verify the threshold boundary.

**Verdict:** Classification is correct. Auditability gap is real — the output doesn't
expose enough information at basic/extended levels for an independent observer to
verify the classification.

**Suggested fix (medium):**
- Add threshold context to the CVD signal's data section (not just meta). Example:
  add `"threshold": 0.10` to `SignalCVD` struct, populated by Compute.
- Or inline the threshold in the summary: `"CVD ratio 0.4528 ≥ 0.10 → aggressive_buy"`.

### 3. Flow Tension — Missing "winner/bias" verdict

**Code traced:** `internal/metrics/flowtension/v1/compute.go:132-155`

**What happens:**

`ComputeSummary()` has 7 named combos + 1 fallback. The combination from the
audit run: CVD=aggressive_buy, OI=stable, Funding=neutral. None of the 7 named
combos match this pattern, so it falls through to:

```
"Mixed signals — monitor for confirmation."
```

This is correct per the current rules, but the README promises an answer to
"Are buyers or sellers winning right now?" — and this output doesn't deliver one.

**Verdict:** The summary IS a verdict (correctly classified as mixed). The gap is
that no single `bias`/`winner` field exists as a machine-readable directional
signal that agents can act on programmatically.

**Suggested fix (medium):**
- Add a `Bias` field to the `Data` struct (values: `"bullish"`, `"bearish"`, `"neutral"`).
  Compute it from a net score:
  - CVD aggressive_buy = +1, aggressive_sell = −1, else 0
  - OI building = +0.5, unwinding = −0.5, stable = 0
  - Funding positive/overheated = +0.5, negative = −0.5, neutral = 0
  - Total ≥ 1 → bullish, ≤ −1 → bearish, else neutral
- Add the OI `ChangePct24h` sign to the summary text when available.

### 4. Market Regime — "conviction" vs "confidence" naming collision

**Code traced:** `internal/metrics/marketregime/v1/compute.go:24-32,93-109`,
`types.go:13-17,41-45`

**What happens:**

Two distinct concepts share confusing names:

| Field | Location | Derivation | Meaning |
|-------|----------|------------|---------|
| `conviction` | `data` | LP ratio band (0.06 → low, <0.07) | **Market structure**: how much trading volume supports current prices |
| `confidence` | `meta` | weighted boolean (cold start, degraded, missing ref) → high/medium/low | **Data quality**: how reliable the regime classification is |

In the audit output: `"conviction": "low"` (low market conviction) + `"confidence": "high"`
(high data quality). This reads as contradictory — "not confident" vs "very confident".

**Verdict:** Both concepts are legitimate and correctly computed. The naming is
the problem. `conviction` is a domain term for liquidity-driven market conviction,
while `confidence` is a data-science term for model trustworthiness. They sound
identical to both humans and LLMs.

**Suggested fix (low):**
- Rename `conviction` → `liquidity_conviction` in the `Data` struct. Backward-compatible:
  keep `conviction` as a deprecated alias for one release cycle.
- Document the distinction in `docs/metrics/market-regime.md` and `agents.md`.

### 5. Market Regime — "do not increase exposure" recommendation

**Code traced:** `internal/metrics/marketregime/v1/compute.go:193-194`

**What happens:**

The Consolidation regime summary is hardcoded:

```
"Dominance neutral, breadth mixed — Consolidation. Market seeking direction; do not increase exposure."
```

This fires when `conviction` is NOT `"high"` (i.e., lp_ratio < 0.15). The audit
rightly notes this contradicts bullish signals from Fear & Greed (20 = Extreme Fear)
and China M2 (+9% YoY = Expanding).

The regime classifier intentionally does NOT cross-reference other metrics —
it's a self-contained structural classification. The recommendation is conservative
by design because Consolidation = no clear directional edge.

**Verdict:** Design choice, not a bug. The regime classifier is supposed to be a
structural layer, not a trading recommendation engine. However, the imperative
"do not increase exposure" reads as an instruction to LLM agents that may
contradict other metrics.

**Suggested fix (low):**
- Soften the language: `"Market seeking direction — consider waiting for confirmation
  before increasing exposure."` This maintains the cautious stance without being
  an absolute command.
- Add a `flags` array to the Data struct listing regime-implied conditions
  (e.g., `"conservative_positioning"`, `"no_directional_edge"`) that agents
  can evaluate against other metrics.

### 7. Full detail mode — thresholds and reasoning stay in meta

**Code traced:** `cmd/cryptospect-cli/meta_processing.go:11-16,57-61`

**What happens:**

The `--detail` flag only controls the `meta` section. Core `data` is identical
at all three levels. The `fullDetailOnlyFields` list strips `thresholds` and
`description` at `extended` level; at `basic`, meta is omitted entirely.

This means an LLM consumer at `--detail full` finds thresholds/descriptions in
`meta.thresholds` and `meta.description` alongside cache metadata — not colocated
with the values they describe in `data`.

**Verdict:** Architectural choice made early in the project. The audit's suggestion
to move threshold/interpretation/confidence into `data` is valid for LLM consumers
that parse structured JSON but don't traverse sibling `meta` objects naturally.

**Suggested fix (medium, breaking for some consumers):**
- Add `thresholds` to the `Data` struct of metrics where they're critical for
  interpretation: flow-tension (CVD/OI/Funding thresholds), dominance (dead bands),
  market-regime (breadth/conviction/dominance thresholds).
- Keep `description` in meta but reference it from `data.methodology`.
- This is a breaking change for any consumer parsing the `Data` struct shape.
  Coordinate with `agents.md` updates.
